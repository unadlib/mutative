title: Patches
description: Record the changes of a recipe as patches, and apply them to a state with apply().
---

With the `enablePatches` option, `create()` also returns the patches that turn the base state into the next state, and the inverse patches that turn the next state back into the base state. [`apply()`](/docs/api-reference/apply) applies them, for example to replay changes on another copy of the state, to send them over a network, or to undo and redo changes.

## Generating and applying patches

```ts
import { apply, create } from 'mutative';

const baseState = {
  foo: 'bar',
  list: [{ text: 'todo' }],
};

const [state, patches, inversePatches] = create(
  baseState,
  (draft) => {
    draft.foo = 'foobar';
    draft.list.push({ text: 'learning' });
  },
  {
    enablePatches: true,
  }
);

expect(patches).toEqual([
  { op: 'add', path: ['list', 1], value: { text: 'learning' } },
  { op: 'replace', path: ['foo'], value: 'foobar' },
]);
expect(inversePatches).toEqual([
  { op: 'replace', path: ['list', 'length'], value: 1 },
  { op: 'replace', path: ['foo'], value: 'bar' },
]);

expect(apply(baseState, patches)).toEqual(state);
expect(apply(state, inversePatches)).toEqual(baseState);
```

`enablePatches` also works with curried producers, manual drafts and [`makeCreator()`](/docs/api-reference/makecreator), and it supports objects, arrays, Maps, Sets, and the values that a [`mark`](/docs/advanced-guides/mark) makes draftable; pass the same `mark` to `apply()`.

## Patch behavior

- **Operations and paths.** Patches use `add`, `remove` and `replace`. A path leads from the root to the changed value through object keys, array indices, Map keys as they are, objects and arrays included, and the positions of Set items. A recipe that returns a new state gets one `replace` patch with an empty path.
- **Order.** The patches of a nested draft come before those of its parents, as in Immer.
- **Values.** A patch value is the object that the next state holds, frozen with it when `enableAutoFreeze` is on. The exception is a changed draft held by a container that the recipe first read after the draft, as in `const item = draft.a; item.x = 1; draft.b.item = item;`: the container's patches carry a copy of the draft's final value, which the next state does not hold and auto-freeze does not freeze. Copy a patch value before changing it. `apply()` copies patch values before applying them.
- **Arrays.** By default, `shift()`, `unshift()`, `splice()`, `reverse()` and `sort()` emit a `replace` patch for each index whose element changed, and an `add` patch for each index past the old length. An array that gets shorter gets one `replace` patch of its `length` by default, or a `remove` patch for each index it loses with `arrayLengthAssignment: false`. Patches preserve holes in both directions: filling a hole takes a `replace` patch, and recreating one rebuilds the array from its index; see [Sparse arrays](#sparse-arrays). With `arrayPatchStrategy: compactArrayPatches`, elements that stay in order stay out of the patches; see [Compact array patches](#compact-array-patches).
- **Maps.** `set()` emits an `add` patch for a new key and a `replace` patch for an existing one, and `delete()` a `remove` patch.
- **Sets.** Patches add an item by its value and remove one by the value it holds; see [Sets of objects](#sets-of-objects).
- **Moved drafts.** A changed draft that leaves its key, because `sort()` or an assignment moved it or another value replaced it there, emits no patches under its old path; the patches of its parent carry its value.
- **Applying patches.** `apply()` applies `add`, `remove` and `replace` patches and accepts `-` as the index that appends to an array. It throws for other operations and for paths through `__proto__` or `constructor`. It takes the `enableAutoFreeze`, `strict` and `mark` options, or `mutable: true` to change the state in place, which throws for a patch that replaces the root state with another value, and it changes a draft in place.
- **JSON Patch.** With `pathAsArray: false` and `arrayLengthAssignment: false`, patches of JSON-compatible objects and arrays are JSON Patch operations. Maps, Sets and array holes have no JSON counterpart.

[Comparison with Immer](/docs/extra-topics/comparison-with-immer#patches) lists where these patches differ from Immer's.

## JSON patches

`enablePatches` takes `true`, or an object that sets the shape and array representation of the patches. With `pathAsArray: false` and `arrayLengthAssignment: false`, patches of JSON-compatible objects and arrays are [JSON Patch](https://datatracker.ietf.org/doc/html/rfc6902) operations, which other JSON Patch libraries can apply ([related discussion](https://github.com/unadlib/mutative/issues/6)).

### pathAsArray - default: true

With `pathAsArray: false`, a path is a JSON Pointer string instead of an array of keys:

```ts
import { create } from 'mutative';

const [state, patches, inversePatches] = create(
  { list: [1, 2, 3] },
  (draft) => {
    draft.list.length = 0;
  },
  {
    enablePatches: {
      pathAsArray: false,
    },
  }
);

expect(state).toEqual({ list: [] });
expect(patches).toEqual([{ op: 'replace', path: '/list/length', value: 0 }]);
expect(inversePatches).toEqual([
  { op: 'add', path: '/list/0', value: 1 },
  { op: 'add', path: '/list/1', value: 2 },
  { op: 'add', path: '/list/2', value: 3 },
]);
```

A string path holds only strings, so it cannot name a Map key that is not a string, or a symbol key: with `pathAsArray: false`, the patch of `draft.set(1, 'b')` would set the key `'1'`. Keep the default array paths for such keys; development builds throw an error when a string path would hold one.

### arrayLengthAssignment - default: true

Setting `arrayLengthAssignment: false` makes an array that gets shorter get a `remove` patch for each index that it loses, instead of a `replace` patch of its `length`:

```ts
import { create } from 'mutative';

const [state, patches, inversePatches] = create(
  { list: [1, 2, 3] },
  (draft) => {
    draft.list.length = 0;
  },
  {
    enablePatches: {
      arrayLengthAssignment: false,
    },
  }
);

expect(state).toEqual({ list: [] });
expect(patches).toEqual([
  { op: 'remove', path: ['list', 2] },
  { op: 'remove', path: ['list', 1] },
  { op: 'remove', path: ['list', 0] },
]);
expect(inversePatches).toEqual([
  { op: 'add', path: ['list', 0], value: 1 },
  { op: 'add', path: ['list', 1], value: 2 },
  { op: 'add', path: ['list', 2], value: 3 },
]);
```

With `compactArrayPatches`, the option applies where an array loses elements at its end or the strategy leaves it to the default; the `remove` patches of a deletion before the end do not depend on it.

<Callout type="idea">
A `remove` patch per index takes more time and more patches for large arrays than one `replace` patch of the `length`, so leave `arrayLengthAssignment` on unless the patches must be JSON Patch operations.
</Callout>

## Compact array patches

By default, patches compare array slots, so an element that moved to a new index takes a patch although nothing about it changed: removing the first of 10,000 elements takes 10,000 patches. Compact array patches keep elements that stay in order out of the patches. Opt in by passing [`compactArrayPatches`](/docs/api-reference/compactarraypatches) as `arrayPatchStrategy`; bundlers drop it unless you import it:

```ts
import { compactArrayPatches, create } from 'mutative';

const baseState = { list: [1, 2, 3, 4] };
const [state, patches, inversePatches] = create(
  baseState,
  (draft) => {
    draft.list.splice(1, 1);
  },
  {
    enablePatches: {
      arrayPatchStrategy: compactArrayPatches,
    },
  }
);

expect(state).toEqual({ list: [1, 3, 4] });
expect(patches).toEqual([{ op: 'remove', path: ['list', 1] }]);
expect(inversePatches).toEqual([
  { op: 'add', path: ['list', 1], value: 2 },
]);
```

On a list of 1,000 small objects, the forward patches of these recipes take:

| Recipe | Default patches | Default bytes | Compact patches | Compact bytes |
| --- | ---: | ---: | ---: | ---: |
| `draft.shift()` | 1,000 | 63,658 | 1 | 28 |
| `draft.splice(500, 2, item)` | 500 | 31,982 | 2 | 92 |
| `draft.push(item); draft.shift()` | 1,000 | 63,673 | 2 | 86 |
| Inserting at two places | 1,002 | 63,789 | 2 | 115 |
| Moving one element within the array | 981 | 62,515 | 2 | 87 |
| `draft.list = draft.list.filter(...)` | 1 | 25,798 | 1 | 37 |
| `draft.reverse()` | 1,000 | 63,671 | 1,000 | 63,671 |

The generator compares the final array with the base array by identity, so the patches are the same however the recipe made the change: with array methods, index assignments or `length` writes, in strict mode or with `mark`. It trims the common start and end, then keeps a longest run of elements that stay in order. Between two kept elements, it replaces as many elements as both sides have, and removes or adds the rest. It emits `remove` operations in descending index order, then `add` operations in ascending index order, then `replace` operations; inverse patches are planned independently for the opposite direction. Patches of JSON-compatible states replay after JSON serialization, and ordinary appends, pops and tail truncations keep the existing efficient patch forms.

A recipe that assigns a new array over the one at a key gets the same treatment, as in `draft.list = draft.list.filter(...)`, `draft.list = [...draft.list, item]` or `draft.list = draft.list.map(...)`: the elements that it left alone need no patches. Where that would not be smaller, as for an array of new values, it stays one `replace` patch of the whole array. A value that a recipe returns replaces the state with one patch, as without this option.

Kept elements may also change in place: where an element keeps its index, the patches of its own draft carry the change, and a `replace` patch at its final index does where the element moved, or where the array holds a draft of it that the recipe read through another path or that another producer created. An element edited before the deletion below keeps its index, so its own patch carries the edit:

```ts
import { compactArrayPatches, create } from 'mutative';

const baseState = {
  todos: [
    { id: 0, done: false },
    { id: 1, done: false },
    { id: 2, done: false },
  ],
};
const [, patches] = create(
  baseState,
  (draft) => {
    draft.todos[0].done = true;
    draft.todos.splice(1, 1);
  },
  { enablePatches: { arrayPatchStrategy: compactArrayPatches } }
);

expect(patches).toEqual([
  { op: 'replace', path: ['todos', 0, 'done'], value: true },
  { op: 'remove', path: ['todos', 1] },
]);
```

The generator leaves an array to the default patches where those are about as small, as they are for `reverse()` and for others that keep few elements in order, for a few assigned indices, and for a deletion that leaves only a short tail. So does it for sparse arrays, and where the patches of a child would change another element. It counts patches rather than measuring their values, so it does not promise the smallest possible patches, and it does not record the recipe's exact operations.

Only arrays with moved or assigned elements pay for this: changing an element in place costs what it costs by default. Finding the common start and end takes **O(n)** time, and matching the elements between them **O(n log n)**. A pure insertion or deletion is faster than default patches, as it builds no patch per moved element. Matching elements after a sliding window or a move can take longer than default patches, up to about three times once the code is warm, in exchange for their size. Applying compact patches is faster in every such case, as `apply()` has far fewer patches to run.

Compact patches use the same `add`, `remove` and `replace` operations and work with array paths or JSON Pointer paths. For a strict [RFC 6902](https://datatracker.ietf.org/doc/html/rfc6902) consumer, combine the strategy with both JSON options:

```ts
const options = {
  enablePatches: {
    arrayPatchStrategy: compactArrayPatches,
    pathAsArray: false,
    arrayLengthAssignment: false,
  },
} as const;
```

<Callout type="warn">
Compact patches make patches smaller; they promise nothing else. They replay final values, so they do not preserve a JavaScript alias graph between inserted values and other paths. They do not give elements identities: an element that moved and changed takes a `replace` patch, and whether an element stays out of the patches depends on the shape of the whole change, with no signal when an array is left to the default patches. Applying them to a CRDT therefore avoids rewriting unchanged elements only where that happens, and cannot provide concurrent conflict resolution. Apply patches to their matching base snapshot in a local CRDT transaction and synchronize native CRDT updates, rather than broadcasting patches as a merge protocol.
</Callout>

## Sparse arrays

A hole is an absent index, which differs from an own index whose value is `undefined`: array methods such as `map()` and `forEach()` skip holes. Patches and inverse patches preserve this distinction, including when a recipe lengthens an array, fills a hole with `undefined`, or moves holes with an array method.

```ts
const base = new Array<number>(2);
base[0] = 1;

const [state, patches, inverse] = create(base, (draft) => {
  draft.unshift(0);
}, { enablePatches: true });

expect(2 in state).toBe(false);
expect(2 in apply(base, patches)).toBe(false);
expect(1 in apply(state, inverse)).toBe(false);
```

An index patch carries a value, so it cannot represent a hole. Filling a hole takes a `replace` patch, but the patches that recreate a hole shorten the array to its index, lengthen it again to leave holes, and restore the elements after it, so their number grows with those elements: filling a hole before 10,000 elements yields one patch and 10,002 inverse patches. A recipe that makes a hole before the last element gets such patches, and inverse patches that fill it. Holes that an array gets past its old length need only a `replace` patch of its `length`. These patches preserve the array itself for mutable application and application on a draft, also inside a Set.

With `arrayLengthAssignment: false`, truncation still uses per-index `remove` patches, but recreating holes needs a `replace` patch of `length`. Apply these patches with Mutative's `apply()`: sparse arrays are JavaScript data, not JSON data, so their patches are not portable JSON Patch operations. JSON serialization turns array holes into `null` and cannot preserve their structure.

## Undo and redo

The inverse patches of each change undo it, and its patches redo it:

```ts
import { apply, create, type Patches } from 'mutative';

let state = { todos: [] as string[] };
const undoStack: { patches: Patches; inversePatches: Patches }[] = [];

function update(recipe: (draft: typeof state) => void) {
  const [nextState, patches, inversePatches] = create(state, recipe, {
    enablePatches: true,
  });
  state = nextState;
  undoStack.push({ patches, inversePatches });
}

update((draft) => {
  draft.todos.push('learn Mutative');
});
update((draft) => {
  draft.todos.push('use patches');
});

const last = undoStack.pop()!;
state = apply(state, last.inversePatches);
expect(state.todos).toEqual(['learn Mutative']);

state = apply(state, last.patches);
expect(state.todos).toEqual(['learn Mutative', 'use patches']);
```

[travels](https://github.com/mutativejs/travels) builds undo and redo with history limits, archives and persistence on these patches, and [use-travel](https://github.com/mutativejs/use-travel) and [zustand-travel](https://github.com/mutativejs/zustand-travel) bring it to React and Zustand.

## Sets of objects

Patches add a Set element by its value and remove one by the value it holds, so a `remove` patch removes an object only from a Set that holds that same object. A Set whose elements changed in place, without any element added or removed, gets patches under the position of each changed element, and they replay in both directions. Once a recipe adds or removes elements of a Set, the Set's `remove` and `add` patches carry every changed element by value instead. `apply()` copies the value of each patch before applying it, so a Set that `apply()` changes holds copies of the objects that patches add, and the inverse patches cannot remove those copies: an undo after a redo leaves the object in the Set. `apply()` also appends every element that it adds, so a Set that it changes can hold its elements in another order than the state that the recipe produced: a changed element of a Set that also added or removed elements, or an element that inverse patches add back, moves to the end, and a recipe that deletes an element and adds it back moves it to the end without a patch. The positions in the patches of a later recipe then find other elements, and its changes under them apply to another element without an error. Sets of primitives keep their elements, but their order can change in the same way. When patches are replayed on states that `apply()` returned, as undo, redo and synchronized copies do, keep such objects in a Map keyed by an id or in an array instead.
